01 — Foundations

Design principles

Six commitments that every product team in the ecosystem designs against, from the enterprise console to a voice-first mobile app in a low-literacy context.

01

Language first

Language is a core product interaction, not a settings-menu afterthought. It is surfaced early, never buried.

02

AI without complexity

Technical complexity — models, tokens, confidence math — stays hidden behind simple, understandable interactions.

03

Accessible by default

We design for different languages, literacy levels, abilities, devices, and interaction methods from the first draft, not as a retrofit.

04

Calm intelligence

Whitespace, hierarchy, and restrained emphasis do the work that decoration would otherwise be asked to do.

05

Consistency at scale

Components behave predictably across products, while still flexing to product-specific needs.

06

Human control

Every AI-assisted result gives visibility into what happened, and a clear way to edit, retry, or undo it.

Typography — usage guidance

Do
  • Set Indic scripts 5–10% larger than adjoining Latin text at the same semantic level — most Indic scripts read smaller at equal font-size.
  • Increase line-height for Indic paragraphs (1.6–1.7) versus Latin body (1.5).
  • Let headings reflow to two lines rather than shrinking type to fit one.
Don't
  • Don't assume a Latin-script heading's width when placing a translated Indic heading — expansion is common.
  • Don't apply letter-spacing to Indic scripts; tracking that improves Latin legibility breaks conjunct formation.
  • Don't mix more than two type families in one interface.

Button — component documentation

Core
Purpose & anatomy
  • Triggers a single, immediate action. Anatomy: optional leading icon, label, optional state indicator.
  • Variants: primary, secondary, ghost, destructive, AI action, icon-only.
  • States: default, hover, pressed, focus, disabled, loading, success.
Do
  • Use exactly one primary button per view for the main action.
  • Keep labels as verbs: "Translate," "Generate," never "Submit."
  • Swap label for a loading state on async actions over 400ms.

17 — Feedback

Error & recovery

Every error names what happened and gives a concrete next step — never a dead end.

AI failure

We couldn't process this audio.

Try uploading a clearer recording, ideally in a quiet space.

Network failure

You're offline.

Your draft is saved. Reconnect to continue translating.

Error message anatomy

Every error states
  • What happened — in plain language, no error codes as the headline.
  • What the user can do — one clear sentence.
  • Recovery action — a single, obvious button.
Variants
  • Inline error — form validation, appears beneath the field.
  • Component error — a single card or panel failed to load.
  • Full-page error — the whole service is unavailable.

23 — Guidelines

Multilingual design guidelines

Rules that keep the system honest across twenty-two-plus languages, not just the one it was designed in.

Text & layout

  • Text expansion — containers flex; German/Malayalam strings can run 30–40% longer than English.
  • Script variation — never hardcode a Latin-script line height or letter width.
  • Alignment — support right alignment and script-appropriate justification where relevant.
  • Line height — Indic body copy uses 1.6–1.7 versus 1.5 for Latin.

Data & interaction

  • Number formatting — supports both international and Indian digit grouping (1,00,000 vs 100,000).
  • Date/time — localizes format and calendar convention per locale.
  • Search — native-script queries and phonetic/transliterated input both resolve correctly.
  • Voice — every core flow has a spoken equivalent, not just a typed one.
